# Pedalboard planner

> Generated by `scripts/build.py`. Edit `catalog/` and `projects/*/project.json`, not this file.

Plans the owner's pedalboards (one folder per board, a *project*) from one shared catalog of pedals, power supplies and cables: checks the signal chain and the power wiring, checks that every plug and cable fits on the Pedal Playground layout, routes every cable (signal and DC) for its minimum length, and proposes better pedal positions. All lengths are in mm.

## Setup

Python 3.12 and [uv](https://docs.astral.sh/uv/). Dependencies: Pillow (images), pytest (dev); the two editors need Tkinter and a display.

```
uv sync                  # once: creates .venv with the dependencies (pyproject.toml, uv.lock) and the `pb` command
uv run pb --help         # every command; uv run pb <command> --help: its options
```

Every command also runs as `uv run scripts/<script>.py ...` (same arguments). Pedal and board images and Pedal Playground's catalog are downloaded on demand into the git-ignored `.cache/` (no images in the repo).

## Commands

| Command | Script | What it does |
|---|---|---|
| `uv run pb build [project...] [--images]` | `build.py` | Validate every project (or the named ones) and regenerate the READMEs, `signal-chain.mmd`, `power.mmd`, `routing.svg`, `power.svg`. `--images`: also `routing.local.svg` with the pedal images (git-ignored). Exit status 1 on validation errors. |
| `uv run pb fetch <project> [--share LINK] [--dry-run]` | `fetch_playground.py` | Read the project's public Pedal Playground layout into `playground_design.json` (the replaced version goes to `playground_history/`, git-ignored). `--share`: a share link or slug (saved in project.json when it has none); `--dry-run`: fetch and compare, write nothing. |
| `uv run pb propose <project> [options]` | `propose_layout.py` | Layout proposals in `projects/<name>/proposals/` (shown in the project README; never touches `playground_design.json`). `--max-change fix\|rearrange\|free` (default fix: small moves, no swaps or rotations), `--max-move-mm MM\|none`, `--seed S`, `--iterations N`, `--restarts R`, `--top N` (default 3), `--pin ID ...` (pedals that must not move), `--dry-run` (report only), `--score` (term breakdown of the owner's layout, then exit). |
| `uv run pb new <name> --instrument guitar\|bass [--share LINK]` | `new_project.py` | Scaffold `projects/<name>/project.json` (board and power wiring left unknown on purpose). |
| `uv run pb migrate-preferences [project...] [--dry-run]` | `migrate_preferences.py` | One-off: move the old per-pedal keys into `pedals.<pedal id>` (`--dry-run` prints the diff). |
| `uv run pb pedal-editor <catalog id> [--footswitches] [--image FILE] [--refresh]` | `pedal_editor.py` | Tkinter editor: place a pedal's (or supply's) jacks, or with `--footswitches` its footswitches, on its image (J / F switch modes, Ctrl+S saves to `catalog/jacks.json` / `footswitches.json`). `--image`: a local PNG; `--refresh`: download the image again. |
| `uv run pb pedal-editor --list` / `--list-missing [project...] [--only jacks\|footswitches]` | `pedal_editor.py` | Jack and footswitch counts per catalog id / what the projects still miss, with the commands to fix it. |
| `uv run pb board-editor <project> [--piece P] [--image FILE]` | `board_editor.py` | Tkinter editor of `projects/<name>/board.json`: hole / filled boxes, edge crossings, the usable area (bounds, key B), for every piece of a composed board (`--piece`: image name or 1-based number; Tab = next piece, W = overview, E = effective holes, Ctrl+S saves). |
| `uv run pb board-editor --list` | `board_editor.py` | Every project's board image(s), derived holes, edit boxes and bounds. |
| `uv run pb outlines [project...] [--image NAME] [--refresh]` | `outlines.py` | Pedal outlines and bodies from the images into `catalog/outlines.json` (existing entries kept unless `--refresh`). |
| `uv run pb boards [project...] [--image NAME] [--refresh]` | `boards.py` | Board holes from the board images into `catalog/boards.json` (`--refresh` recomputes only the holes). |
| `uv run pb test [pytest args]` | `pytest tests -q` | The tests (several minutes; `PEDALBOARD_SLOW=1` adds the full guitar-gig search). |

Typical loop: arrange the pedals in Pedal Playground, `uv run pb fetch <project>`, `uv run pb build <project>`, read the project README (findings, cables to buy, routing.svg), optionally `uv run pb propose <project>` and build again.

## Files

```
catalog/pedals.json           everything that is part of a pedal (specs, power, bypass, digital, tags, height, intrinsic rules)
catalog/power_supplies.json   supply models: outputs, voltages, current limits, how many you own
catalog/cables.json           cable and plug types (patch, instrument, power, expression; plug head sizes and sources)
catalog/jacks.json            jack positions per pedal/supply (fractions of the Pedal Playground image; pb pedal-editor)
catalog/footswitches.json     footswitch positions and types per pedal ([] = no footswitch; pb pedal-editor --footswitches)
catalog/outlines.json         pedal shapes and bodies derived from the images (pb outlines)
catalog/boards.json           board holes derived from the board images (pb boards)
projects/<name>/project.json  everything that can change: board, chain order, rules, power wiring, cables, layout search, per-pedal preferences (pedals.<id>)
projects/<name>/board.json    the owner's hole / edge / usable-area corrections (pb board-editor)
projects/<name>/playground_design.json   the owner's Pedal Playground layout (pb fetch)
projects/<name>/README.md, *.mmd, routing.svg, power.svg   generated by pb build (never edit by hand)
projects/<name>/proposals/    layout proposals (pb propose)
docs/TODO.md                  backlog and open questions; docs/plans/ the design record of each feature
```

## Model

Footswitches: spacing is comfort, so the layout proposals push switches of different pedals apart (crowding = priority x (comfort - distance)^2 / comfort below `footswitches.comfort_mm`, default 100 mm). An optional `footswitches.min_distance_mm` makes closer pairs findings. Missing footswitch data and pairs below the minimum are warnings unless `validation.require_footswitches` / `validation.strict_footswitches` are set. Toppers (`footswitches.toppers`, a finishing step after the layout; the search ignores them) add `footswitches.topper_bonus_mm` (default 4.5 mm: the height a topper adds, a rough proxy, unverified) per topper to a pair's effective distance; the build suggests the few that remove the most crowding (and shadow). Heights (`height_mm` of the catalog; `footswitches.heights: false` = off, estimates): a pair at different heights gains a step in its effective distance (`footswitches.height_gain` 0.5 x the difference, at most `footswitches.height_cap_mm` 10 mm of it; toppers do not enter it), and a switch with a taller switch of another pedal in the path of the foot in front of it is shadowed (`footswitches.foot_width_mm` 80, `footswitches.foot_length_mm` 190, `footswitches.foot_pitch_deg` 5, `footswitches.deck_rise_mm` 0, `footswitches.reach_weight` 1, optional `footswitches.max_shadow_mm` = a finding; the layout proposals minimise it with `layout.weights.reach`).

Per-pedal wishes live in `pedals.<pedal id>` of project.json, every field optional: `position` {`side` left|right|any, `depth` front|back|avoid_front|any, `weight` (score per mm, default 0.3), `strength` preferred|required}, `pin`, `rotations` ([0, 90, 270], "any" or "current"), `order` {`<name>`: an ordering rule without id / pedal; its id is `<pedal>.<name>`}, `power` {`own_output`, `supply`, `port`, `voltage_v`, `strength`}, `toppers` (switch ids), `note`. Each project README has a "Preferences" table: is every wish met in the owner's layout and in each layout proposal; a required position or power wish that is not met is a warning (an error with `validation.strict_preferences`). The layout search and the power assignment read the wishes. The older per-pedal keys (`rules` entries, `layout.pins`, `layout.rotations.<id>`, `layout.access.pedals`, `footswitches.toppers`) still work; `uv run pb migrate-preferences [project...] [--dry-run]` moves them into the profiles.

Every project has `validation.no_unknown` on by default: any missing (`null`) value for a pedal, supply or board the project uses fails the build until you fill it in.

Jacks: pedals with no jack setup, and cable space blocked in `playground_design.json`, are warnings by default; set `validation.require_jacks` / `validation.strict_clearance` to make them errors. A pedal or on-board supply whose body (the enclosure from its image, `catalog/outlines.json` `bodies`; jacks may overhang; the box without body data) lies outside the usable board area (the four lines of `board.json` `bounds`, drawn in the board editor; the board edges without them) is a warning, an error with `validation.strict_bounds`; under-board supplies are never checked. Signal jacks are checked against the plug head of the project's patch cable type (`cables.type`, catalog/cables.json) on the exit side the router chose, power jacks against the DC plug type (`cables.power_type`; with `cables.power_types` the router picks the type per plug) on the less blocked side (or the small `jacks.power_clearance` zone without one); other jacks use the fixed zone `jacks.clearance.outward_mm` / `side_mm` (default 6.3 / 7 mm). Plugs and fixed zones of different jacks that overlap each other are reported as plug collisions (same severity as blocked space; the side choice avoids them where it can). All cable figures are in mm.

### Known limitations

- Guitar to first pedal and last pedal to amp cables are not modelled (the guitar and amp positions are not in the layout).
- Pedals are their outlines from the images (`catalog/outlines.json`; `uv run scripts/outlines.py` adds or refreshes them), so jack bumps and rounded corners are not obstacles; Pedal Playground's box is used only where an outline is missing and for overlaps in the layout. Signal and power plugs are modelled from catalog/cables.json (Ernie Ball flat patch plugs and right-angle DC plugs; several head dimensions are estimates, see the `verified` lists there); extra and guitar/amp jacks keep a fixed clearance zone (6.3 mm outward, 7 mm to each side by default; a used extra jack with a straight plug type, `cables.extra_type`, gets that plug's box), power jacks without `cables.power_type` the smaller `jacks.power_clearance` zone.
- Extra jacks (Exp, Tap, Thru, Stereo, XLR ...) are in the catalog for a complete description only; add one to a project's `jacks.extra_used` when it is actually plugged in, so its cable space is checked.
- Jack points were placed by hand: re-check any pedal whose zone shows more than a few percent on the pedal body in the pedal editor (the PolyTune 3 was marked before the edge-of-jack guidance).

### Data to verify

- Power specs re-checked on 2026-10-21; still retailer-only or unpublished: Sun Face current (1 mA unverified), Full-Drive 2 and Mini Ego current, E-Lady, Danelectro 3699 and Carbon Copy figures, and the maximum voltage of most 9V pedals (their 9V is a rating, not an explicit limit).
- PastFX Reticon: the 50 mA draw and isolated-supply need come from search snippets of the maker's pages.
- Browne Protein V3 current: 130 mA planned (manual says under 100 mA, a Q&A line says 130 mA, retailers about 30 mA). The price in the catalog is for the V4.
- Version assumptions: Retrovibe is priced and measured as the mk.4; the layout uses the Mini Beano Boost while the catalog entry is the Beano Boost.
- The Harley Benton ISO-5 Pro has no Pedal Playground entry: the practice and bass layouts show the ISO-1AC Pro image as a stand-in (its outputs marked by the owner).
